## 6. Reset 数据风险发现与处置

首次真实执行 `resetBeforeImport=true` 时，导入任务本身成功，但验收发现 reset 删除了既有学生学习数据。

部署前关键计数：

```text
practice_sessions = 30
practice_attempts = 142
wrong_questions = 42
student_sessions = 23
```

原因：

- reset 删除 corpus；
- practice/session/attempt/wrongbook 表通过外键依赖 corpus；
- PostgreSQL cascade 删除了依赖数据。

处置：

1. 立即停止把 reset success 当作发布成功证据。
2. 从部署前 dump 恢复目标数据库。
3. 重新执行 migration `0012/0013`。
4. 复核题库、账号和学习数据计数。
5. 新增 `ADMIN_IMPORT_ENABLE_RESET=false` 默认门禁。
6. 保留 `ADMIN_IMPORT_ENABLE_WRITE` 与 reset gate 的独立性。
7. 验证 super_admin 在 reset gate 关闭时收到 422，表计数不变。
8. 验证 `resetBeforeImport=false` 全量导入成功，学习数据计数不变。

## 8. 负载与主机容量结论

首次完整 load baseline：

```text
checks = 27
failures = 0
health p95 = 280.54 ms
readiness p95 = 48.30 ms
metrics p95 = 43.88 ms
banks p95 = 1348.46 ms
student login p95 = 132.07 ms
practice create p95 = 98.14 ms
admin login p95 = 110.19 ms
```

在恢复后连续执行多次全量非 reset import，并立即再次启动认证 load baseline 时，目标主机出现 SSH banner 与 API 响应超时。重启后读取上一 boot 的 `sysstat`、API journal 和 Nginx log，已经确定主因不是网络流量跑满，也没有发生 OOM kill，而是**块设备 I/O 饱和和大量不可中断 I/O wait**：

```text
server CPU = 2 vCPU
server memory = 1.6 GiB
load average = 96.28 / 89.25 / 52.19
blocked tasks = 20
CPU iowait = 60.44%
disk reads = 111597 KiB/s
disk queue depth = 92.64
disk await = 33.34 ms
memory used = 79.07%
swap used = 0
network eth0 rx/tx = about 1 KiB/s
kernel OOM / killed process = none
```

API 日志进一步显示：

- 第一次 load iteration 的 `/api/banks` 为 `1670 ms`；
- 随后的 `/api/banks` 在 `18:18:34` 开始，直到 Nginx `18:19:40` upstream timeout 仍未完成；
- health/readiness/login 后续延迟上升到约 `1.3–15.6 s`；
- synthetic healthcheck 最终超时；
- 同一时期磁盘读队列和 blocked tasks 极高，而公网网卡流量很低。

因此当前结论是：

- 当前单机规格不适合连续全量导入与在线/API 验收叠加；
- importer 的全量 `ON CONFLICT DO UPDATE` 会产生明显写放大、WAL、缓存淘汰和后续表/index 扫描压力；
- 目标主机同时运行 QQ/Electron、Python bot、Docker、云监控等其他服务，可供 PostgreSQL/API 使用的资源更少；
- 当前环境需要维护窗口、操作节流、导入后冷却和健康复核；
- 在提升磁盘/主机规格或优化 importer 前，不支持“连续全量导入 + 在线流量”场景。

## 11. 完成边界与下一步

B9.34 的完成标准已经满足，但它不表示“完整公开生产产品”完成。

仍未完成：

- 正式公网发布与真实用户验收；
- 外部监控/告警目标；
- 长期持续压测；
- 主机容量提升或 importer 性能优化；
- corpus reset 的数据保留/版本化方案；
- Question Review diff/审批/回滚；
- Learning 正式前端；
- 全题型；
- 最终视觉系统。

下一阶段不应立刻做 realtime progress 或全仓 route helper 重构。优先顺序应是：

1. 固化 Import 运维安全：write gate 默认关闭、维护窗口、容量观察、导入后健康检查。
2. 对 staging 做人工学生端/Admin 审核。
3. 根据真实审核反馈选择 Question Review 完整运营流或 Learning 前端 IA。
4. route validation/error mapping 继续作为低风险工程化债务分批收敛。
5. realtime progress 仅在真实管理员明确需要时实现，优先 SSE + polling fallback。
